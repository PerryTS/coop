# Shared runtime providers

This is the mechanism that makes Coop more than "compile each app to a binary".

## The model

`perry-runtime` and `perry-stdlib` are built **once per box** as shared
libraries:

- `libperry_runtime_provider.dylib` / `.so`
- `libperry_stdlib_provider.dylib` / `.so`

Each application is compiled as an **app-only dylib** that resolves against that
ABI instead of embedding its own runtime. The host (`provider-host`, or
`coop-worker` in production) loads the providers first, then `dlopen`s the
application and calls `perry_module_init`.

## Building the providers

```bash
./scripts/build-perry-libraries.sh
```

What it actually does, because it is not obvious from the outside:

1. Temporarily rewrites `perry-runtime`'s manifest to `crate-type = ["dylib"]`
   (restored by a trap on exit, including on failure).
2. Builds it with the symbol-suppression `stdlib` feature so the stdlib provider
   does not re-export the runtime's own surface.
3. Links `coop-perry-stdlib-shared` — the cdylib in `crates/perry-stdlib-shared` —
   against that dylib.

**Coop does not use `.a` archives.** Perry's own documentation tells you to
rebuild `perry-runtime-static` / `perry-stdlib-static` and check that the `.a`
mtime moved. That advice does not apply here and will mislead you: the artifacts
are `.dylib`/`.so`, and the right freshness check is the provider `sha256` plus
the manifest's recorded `perry_commit`.

## The identity guard

Each published application carries a manifest recording:

- the Perry commit it was compiled with
- the provider `compiler_sha256`
- the target triple
- the artifact's own `sha256` and size

`coop-worker` verifies all of this before mapping the image, and **refuses to
load on mismatch**:

```
Perry ABI mismatch for ".../next-bench.dylib":
  compiled with 0.5.1503, host runtime is 0.5.1510
```

That refusal is the feature. An application built against a subtly different
runtime — different GC layout, different NaN-boxing tags, different stdlib
symbol set — would not fail cleanly at load; it would corrupt memory at request
time, hours later, somewhere unrelated.

## Upgrading Perry

The version string is **not** a reliable freshness signal. `0.5.1510` covered
more than a dozen commits including significant runtime changes. Pin and compare
**commits**, which is what `perry-main.lock` records.

After bumping the pin:

1. Rebuild the providers (`build-perry-libraries.sh`).
2. Recompile every deployment — the identity guard will reject stale images.
3. Confirm the provider `sha256` changed and the manifest's `perry_commit`
   matches the new pin.

A fixture or benchmark artifact built by hand will go stale on every bump and
fail the guard. Prefer artifacts that can be regenerated by the daemon from
source; `scripts/prepare-next-benchmark.sh` is the worked example.

## Why not one binary per app

Because the runtime is the bulk of the image. Linking it per application makes
each deployment tens of megabytes and multiplies resident memory by the number of
services on the box. The shared-provider model is what makes "a portfolio of
small services on one machine" a sensible proposition rather than an expensive
one.

The cost is the identity coupling described above: one runtime per box means one
runtime version per box.
